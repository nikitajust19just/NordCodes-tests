# 🏛️ Фреймворк интеграционного тестирования REST API (NordCodes)

Проект представляет собой компонентный автоматизированный фреймворк для сквозного (E2E) и негативного тестирования REST API. Фреймворк проверяет цепочку состояний токена авторизации и валидацию входящих контрактов приложения (конечного автомата сессий).

## 🚀 Стек технологий
* **Язык**: Java 17
* **Тестовый движок**: JUnit 5 (Jupyter)
* **HTTP-клиент**: REST Assured
* **Эмуляция внешних систем**: WireMock (Локальный WireMockServer)
* **Матчеры и проверки**: AssertJ (Soft Assertions)
* **Отчетность**: Allure Framework + Регистрация сетевых вложений (AllureRestAssured)
* **Сборщик проекта**: Maven

---

## 🛠️ Запуск тестов и генерация отчетов

### 1. Локальный запуск тестов
Для запуска тестов с автоматической очисткой старых результатов выполните команду в терминале:
```bash
mvn clean test
```
*Конфигурация логирования REST Assured оптимизирована (применена синглтон-проверка), логи в консоли не дублируются при запуске пачки классов.*

### 2. Генерация и просмотр Allure-отчета
Для сборки отчета и автоматического открытия его в браузере выполните:
```bash
mvn allure:serve
```
*Конфигурация Allure перенаправлена в директорию `target/`. Команда `mvn clean` автоматически очищает кэш прошлых запусков, гарантируя 100% чистоту отчетов.*

## 🏗️ Архитектура тестового фреймворка

Проект спроектирован по слоистой архитектуре с четким разделением ответственности (Separation of Concerns). Отчет разработан с учетом чтения людьми, не связанными с программированием (все шаги обернуты в понятные бизнес-блоки `Allure.step` на русском языке).

### 1. Архитектурные слои:
* **`api.config` (`Config.java`)** — Централизованное считывание переменных окружения и системных свойств (`BASE_URL`, `API_KEY`, `WIREMOCK_PORT`). Поддерживает бесшовную интеграцию с CI/CD (Jenkins/GitLab).
* **`api.generators` (`RandomData.java`)** — Динамический генератор тестовых данных без хардкода. Умеет генерировать как валидные HEX-строки, так и полные алфавитные токены по спецификации ТЗ (`A-Z0-9`).
* **`api.specs` (`RequestSpecs.java`)** — Шаблоны спецификаций REST Assured. Изолируют авторизационные заголовки и прикрепляют фильтры Allure для перехвата HTTP-трафика.
* **`api.steps` (`ApiSteps.java` / `WireMockSteps.java`)** — Шаги-обертки для отправки запросов и управления состоянием заглушек. Инкапсулируют логику `verify` сетевого периметра.
* **`api.tests` (`BaseTest.java`)** — Базовый класс, безопасно управляющий жизненным циклом `WireMockServer` (внедрена проверка `isRunning()`).

### 2. Тестовые классы (Группировка в Allure):
Тесты разделены на 4 изолированных класса для прозрачной аналитики в отчете:
1. **`HappyPathTest`** — Позитивные сквозные сценарии взаимодействия (`LOGIN` ➡️ `ACTION` ➡️ `LOGOUT`).
2. **`ValidationTests`** — Проверки сетевого периметра безопасности при отсутствии `X-Api-Key`, отправка неизвестных экшенов и валидация граничных длин токенов (31, 33, 0 символов) через `@ParameterizedTest`.
3. **`StateMachineTests`** — Проверки устойчивости переходов состояний (повторный вход, логаут мертвой сессии) и **честная изоляция данных** (доказано, что `LOGOUT` одного пользователя не аффектит сессию другого параллельного юзера).
4. **`KnownBugsTests`** — Изолированный набор тестов, фиксирующий известные дефекты бэкенда. Предотвращает ложные падения регрессионного прогона.

## 🐛 Зафиксированные дефекты бэкенда (Реестр багов)

В ходе автоматизации и исследования системы были обнаружены и задокументированы три критических дефекта. В автотестах они помечены аннотацией `@Issue` со статусом `CRITICAL`.

### 🚨 BUG-501: Необработанное исключение при сбое сервиса авторизации
* **Суть проблемы**: Если внешний сервис `/auth` возвращает легитимную ошибку (например, `401 Unauthorized`), тестируемый бэкенд падает с ошибкой `500 Internal Server Error`, вместо того чтобы корректно транслировать статус клиенту.
* **Как проверено**: Симулирован код 401 на WireMock. Тест извлекает JSON-тело ответа, верифицирует структуру и с помощью `verifyPostRequestSent` доказывает, что падение в 500 произошло строго после сетевого обращения бэкенда к сателлиту.

### 🚨 BUG-502: Нарушение спецификации валидации алфавита токена
* **Суть проблемы**: По ТЗ токен должен принимать любые символы из диапазона `A-Z0-9`. По факту регулярное выражение бэкенда пропускает только строгий Hex (`A-F0-9`). При передаче разрешенных по ТЗ букв дальше по алфавиту (например, `G` или `Z`) бэкенд падает в ошибку валидации `400 Bad Request`.
* **Как проверено**: Тест использует генератор `RandomData.getTzToken(32)`, динамически отправляет токен с символами `G-Z` и фиксирует несоответствие бизнес-требованиям.

### 🚨 BUG-503: Необработанное исключение при сбое сервиса бизнес-логики
* **Суть проблемы**: Аналогично первому багу. Если пользователь успешно залогинен, но во время выполнения `ACTION` внешний сервис `/doAction` возвращает ошибку `500`, тестируемый бэкенд не умеет держать удар. Он ломает интеграционный контракт и сам возвращает клиенту наружу `500 Internal Server Error` вместо архитектурно верного `502 Bad Gateway`.
* **Как проверено**: Проверено в классе `KnownBugsTests` путем симуляции падения внешней ручки бизнес-логики с последующей верификацией сетевой активности.
